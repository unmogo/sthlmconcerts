# sthlmconcerts

## What this is

A public list of every upcoming concert and comedy show in Stockholm, live at
https://sthlmevents.lovable.app/. React + Vite front end, Supabase (Lovable Cloud) backend
whose edge functions scrape event sites into Postgres. **This repo is Lovable-managed**:
Lovable commits to `main` and publishes the site.

## Commands

    bun install --frozen-lockfile     install (npm ci fails: package-lock.json is out of sync)
    bun run dev                       dev server on :8080 (predev regenerates the sitemap first)
    bun run build                     production build into dist/ (prebuild regenerates the sitemap)
    bun run preview                   serve dist/
    bun run lint                      eslint; fails today with 7 errors, see Traps
    bun run test                      vitest; fails today, there are no test files

Edge functions have no local runner in this repo; they deploy through Lovable Cloud.

## Layout

- `src/pages/` routes (`/`, `/event/:slug`, `/auth`, `/reset-password`), wired in `src/App.tsx`.
- `src/lib/api/concerts.ts` is the only place the UI talks to the database or edge functions.
  Add new calls there, not inline in components.
- `src/components/ui/` is shadcn/ui; `src/components/header/` holds admin controls.
- `src/integrations/supabase/{client,types,previewAuthStorage}.ts` and `src/integrations/lovable/`
  are generated by Lovable. Do not hand-edit.
- `supabase/functions/<name>/index.ts` one edge function each; shared code in
  `supabase/functions/_shared/` (`sources.ts` is the scraper source list, `venues.ts` venue
  resolution, `firecrawl.ts` and `ai.ts` the external clients, `event-extract.ts` HTML parsing).
- `supabase/migrations/` schema, RLS and DB functions. Lovable names them by timestamp + uuid.
- `scripts/generate-sitemap.ts` writes `public/sitemap.xml` from the live DB.
- `docs/process/` older agent process notes. Useful history, not current truth (see Traps).

## Rules

- The tracked `.env` stays tracked. It holds only the Supabase publishable key, URL and
  project id, which are browser-public; untracking it breaks Lovable builds. Nothing else
  ever goes in it. Local overrides go in `.env.local` (ignored).
- Real secrets (`SUPABASE_SERVICE_ROLE_KEY`, `FIRECRAWL_API_KEY`, `LOVABLE_API_KEY`,
  `SPOTIFY_CLIENT_SECRET`) live only in Supabase function secrets, read with `Deno.env.get()`.
  This repo is public.
- Every edge function sets `verify_jwt = false` in `supabase/config.toml`, so each one must
  check auth itself (admin via the `has_role` RPC, or the service-role bearer for self-chaining).
  A new function without that check is open to the internet.
- Supabase JS calls return `{ data, error }`; destructure and check `error`. `.catch()` on a
  query builder was a real bug in `manage-concerts` (docs/process/changelog.md, 2026-02-24).
- Deleting an event must go through `manage-concerts` so it lands in `deleted_concerts`;
  otherwise the next scrape resurrects it.
- Colors come from the HSL tokens in `src/index.css`, not raw Tailwind color classes
  (docs/process/process-ui.md).

## Traps

- `bun run dev` and `bun run build` rewrite the tracked `public/sitemap.xml` from live data.
  Every local build dirties the tree; do not commit that diff with unrelated work. With no
  network the script warns and writes static routes only, which shrinks the sitemap.
- `predev`/`prebuild` call `bunx`. A Windows Bun install may lack the `bunx` shim and the
  script fails with `command not found: bunx`; `bun x tsx scripts/generate-sitemap.ts` works.
- `npm ci` fails: `package-lock.json` is missing `@testing-library/dom` and friends. Lovable
  keeps `bun.lock` current; use Bun. Two lockfiles (`bun.lock`, `bun.lockb`) plus npm's are tracked.
- `bun run lint` has 7 pre-existing errors (prefer-const, no-useless-escape, a `require()` in
  `tailwind.config.ts`). CI does not run lint until they are fixed.
- `scrape-concerts` does one source per invocation and then POSTs to itself with the service
  role key. A 240 s budget per source keeps it under the 900 s wall clock. Adding a slow source
  or removing the budget check strands the rest of the chain. A watchdog marks jobs failed
  after 12 min without a heartbeat.
- Firecrawl allows about 50 scrapes a minute across all sources; `firecrawl.ts` paces at one
  per 1.4 s. RA runs first because earlier sources used to exhaust the rate limit before it ran.
- Aggregators (LiveSpot, Evently) leak other cities through "related events" blocks;
  `isNonStockholm` in `scrape-concerts` filters them. "Stockholm, Sweden" is not a valid venue.
- evently.se images block hotlinking (`cross-origin-resource-policy: same-origin`), so
  `concert-utils.ts` routes them through the `image-proxy` function.
- `docs/process/architecture.md` and `process-edge-functions.md` describe an older
  batch-numbered, Evently-first scraper. The code now uses the `SOURCES` list and `scrape_jobs`.
  The `trigger_scrape_batch` DB function (migration 20260224012655) posts the old body with
  the anon key, which the current function rejects. No migration defines a cron schedule.
- Dates: `concerts.date` holds Stockholm wall-clock time behind a UTC offset. Render with
  `parseLocalDate` (`src/lib/utils/concert-utils.ts`), which strips the offset; `new Date()`
  shifts times by an hour or two (fixed in commits fadc4db, 1f90a62).
- The anon key is hardcoded in `scripts/generate-sitemap.ts` and that migration. It is the
  public anon role key, not a secret, but never copy that pattern for any other key.

## Repo etiquette

Conventional commits (`feat:`, `fix:`, `docs:`, `chore:`); body says why. Branch per change,
squash-merged PR with what changed / why / how verified / what to watch. Nothing secret or
over 5 MB in git. Lovable's `Changes` auto-commits are the one tolerated exception.
